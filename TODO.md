# AfterRain implementation outcomes

## 1. Responsive product shell, landing page, and visual system — complete

- Build a polished contemporary environmental-intelligence civic operations tool, not a generic admin template: warm off-white background; deep charcoal/dark forest text; muted forest-green primary accent; restrained amber warnings; accessible red critical status with both text and icon; subtle neutral-grey borders; clean surfaces with restrained shadows; softly rounded corners; clear modern sans hierarchy; generous consistent spacing; readable charts; consistent Lucide icons.
- Use the AfterRain brand and a simple original raindrop/recovering-landscape/water-ripple logo. Include responsive desktop sidebar and mobile-friendly navigation, accessible form labels, visible focus states, empty/loading/error states, and explanations/tooltips for non-obvious scores. Avoid excessive gradients, huge decorative headings, and emoji-heavy UI.
- Landing page must show the logo/product name; tagline “When the water recedes, recovery begins.”; a short explanation of the post-flood recovery problem; Report, Prioritize, Recover feature highlights; “Explore Recovery Dashboard” and “Report an Issue” actions; sustainability objectives; and a footer with SDG alignment. Snapshot metrics and queue rows read from current browser-local data.
- All navigation links must lead to functional pages. Mobile and desktop layouts must remain usable.

## 2. Reporting flow, validation, and confirmation — complete

- Provide a mobile-friendly report form with reporter name or anonymous option; category; short title; detailed description; location name; optional latitude/longitude; optional image upload; date/time observed; and optional indication of whether the problem is still active.
- Categories must be Waste and debris; Waterlogging and drainage; Possible water contamination; Road or infrastructure damage; Sewage overflow; Damaged public facilities; and Other environmental recovery issue.
- Validate required fields and coordinate ranges when coordinates are supplied. Restrict image uploads to common image formats and reasonable file sizes. Do not require a photo or precise coordinates. Show a preview before submission and loading, success, and error states.
- Save the report persistently; generate a unique report ID; show the ID in a confirmation page/panel; make it possible to browse submitted reports and their current status. Do not simulate successful saving when saving failed. Surface the selected category, deterministic rule suggestion, reason/confidence, and any human-review flag.
- Show a clear safety notice: do not enter floodwater or approach hazardous sites to gather evidence.

## 3. Shared data, fictional demonstration scenario, and persistence/reset — complete

- Persist reports, incidents, report relationships, assignments/recovery tasks, and status history after refresh. Seed sample data only when no saved application data exists; never overwrite user-created data on every reload. Use stable unique IDs rather than array positions. Recalculate time-sensitive scores when a saved browser store is hydrated.
- Include at least 10 internally consistent fictional reports across 5 or more locations, with varied timestamps, categories, verification states, and statuses. Include three reports describing the same blocked drainage location; two reports about debris accumulating near the same waterway; one possible water-contamination observation requiring verification; damaged public road; sewage overflow; a resolved cleanup incident; and a low-priority maintenance issue.
- Clearly label all fictional locations and incidents as demonstration data; never present them as actual flood reports or verified environmental conditions. Do not invent geographic coordinates for real incidents or seeded sample incidents.
- Provide a one-click reset-demo-data action with confirmation that restores the original scenario without creating duplicate records or breaking the app.

## 4. Deterministic intelligence, duplicate review, and explainable scoring — complete

- Classify using selected category, titles, and descriptions with a small rule-based classifier. Return predicted/retained category, reason, confidence or rule-match indicator, and human-review flag. If ambiguous, retain the user's selected category and flag it for review. Expose that result to reporters and coordinators; use the rule-predicted category as a comparison signal without replacing the user's selected category.
- Compare new submissions with unresolved incidents using matching/related categories, normalized lowercase text with punctuation removed, tokenization, lightweight Jaccard similarity, Haversine distance when valid coordinates exist, and a configurable time window. High text similarity plus distance within 300 metres suggests a likely duplicate; moderate similarity plus distance within 150 metres suggests a possible duplicate. Similar text without location evidence is related/manual review, never automatic merge. Location-name matching without coordinates is a weak signal and must explain uncertainty. Keep thresholds configurable.
- Preserve every original report and its timestamp. Never silently delete or irreversibly merge a report/incident. Present candidate relationships for coordinator confirmation/rejection; keep proposed/confirmed/rejected relationship state and reviewer notes. Proposed reports remain unlinked and excluded from incident totals until confirmed; superseded relationships are rejected; a report moved from its sole-report incident leaves an auditable closed history record, not an empty active queue row.
- Calculate explainable preliminary severity 0–100 from configurable weights: 35% reported impact, 25% potential environmental harm, 20% immediate public-safety concern, 10% infrastructure disruption, 10% supporting evidence and verification; score each factor 0–100. For unreviewed reports derive provisional values from transparent category-specific rules and descriptions; mark provisional. Missing critical information lowers confidence or requests human review. Lack of a photo is not evidence of harmlessness.
- Calculate operational priority separately: 50% severity, 20% time sensitivity, 15% environmental sensitivity, 15% recurrence/persistence; each normalized 0–100. Priority bands: 75–100 High; 45–74 Medium; 0–44 Lower. Show weights/factors and a supported natural-language reason. Explain that this is a prototype decision-support heuristic, not a validated disaster-risk model and not a replacement for official emergency guidance.
- Detect nearby possible hotspots from supplied-coordinate proximity and matching location names; show related incident count, categories, time range, and coordinator-review flag. Explain whether the cluster uses coordinate, place-name, or mixed edges; disclose when a transitive group is not pairwise within the coordinate threshold. Do not claim contamination, disease outbreak, or flood propagation solely from nearby reports.
- Core operation must not depend on a paid AI service. Optional AI must not invent coordinates, verified findings, measured quantities, or emergency instructions, and must not send unnecessary personal information.

## 5. Recovery dashboard, filters, search, and visualizations — complete

- Show total reports received, number of unique incidents, unresolved incidents, high-priority incidents, and completed recovery tasks; clearly distinguish reports from unique incidents. Unique incidents count currently linked report groups only, not proposed matches or empty archive records.
- Show incidents sorted by calculated priority highest first. Each incident row/card shows ID, category, short description, location, linked-report count, severity, priority, priority band, most recent report time, current status, main reason for priority, and recommended next action.
- Provide filters for All incidents, High priority, Unresolved, Resolved, Environmental waste, Water and drainage, Infrastructure damage, and Other. Search by incident ID, description, category, and location.
- Include actual-data bar chart of incidents by category, status breakdown chart, and simple recovery-progress indicator. Metrics/charts/queue update when underlying incidents, reports, or statuses change. Provide useful empty states.

## 6. Incident intelligence detail and coordinator review actions — complete

- For each consolidated incident show ID/title/category/location/status/severity/priority/linked-report count; original descriptions and available photographs from linked reports; timeline of observations and status changes; scoring factors; suggested recovery action; assigned team; and resolution notes.
 - Include a relationship panel explaining why reports were grouped together. Allow a coordinator to confirm or reject a proposed duplicate relationship; link a report to an existing incident; create a separate incident from a report that was incorrectly grouped; change incident status; assign a recovery team; and add notes. Proposed reports are displayed separately from linked report totals until coordinator confirmation.
- Preserve all original reports and timestamps through link/separate operations. Reject stale relationships after re-linking. Do not offer a split action for a sole-report incident. Keep resolution notes, evidence, and verified measured amounts visible after resolution and later incident closure. Unknown incident IDs have a useful route state, not a broken page.
- Do not allow a proposed or manual relationship to add a new report to an incident already Resolved or Closed or rejected. Disable confirmation/link controls with an explanation; a stale proposed report can still be rejected and preserved as a separate incident.

## 7. Recovery map and location explorer — complete

- If Leaflet/OpenStreetMap is feasible, display incidents only at valid coordinates supplied in reports. Use distinct markers for high/medium/low priority. Selecting a marker opens incident details. Category and status filters also apply to markers, with a corresponding incident list.
- Never require a paid map API key or invent geographic coordinates. Clearly distinguish sample locations from verified real-world locations. If an interactive map becomes a blocker, provide a clean schematic/location-based incident explorer instead.

## 8. Recovery planner, assignments, status transitions, and completion evidence — complete

- Turn the priority queue into an actionable recovery plan. For each incident display the problem, why it matters, suggested next action, required skill/team type, current status, and expected completion evidence.
- Use category-appropriate recommendations: waste/debris—organize safe cleanup and segregate recoverable material; blocked drainage—schedule authorized inspection and clearance; possible contamination—request appropriate water-quality testing through a qualified authority; infrastructure damage—request relevant maintenance inspection; sewage overflow—escalate to responsible sanitation authority. Never state suspected contamination as confirmed without verified evidence.
- Let coordinators assign a team, record a recovery task, update progress, and add notes. Use explicit valid transitions among Reported, Under review, Verified, Assigned, In progress, Resolved, and Closed or rejected; prevent invalid transitions and record every status change in history. A resolved task remains completed if its incident is later closed.
- Mark a task resolved only after the resolution workflow is completed and resolution notes/evidence are recorded. Waste quantities may be recorded only when a coordinator enters a finite, non-negative verified amount and unit. For other tasks record relevant completion evidence rather than invented savings.

## 9. Impact/recovery analytics, timestamp calculations, and CSV export — complete

- Calculate from actual application data: reports submitted; unique incidents; duplicate reports linked to existing incidents; verified incidents; completed recovery tasks; waste-cleanup tasks completed; water-quality inspection requests recorded; average report-to-assignment time when sufficient timestamps exist; and average assignment-to-resolution time when sufficient timestamps exist. Count only relationship links that remain current.
- Show incidents created and resolved over time. Charts and statistics update when reports/incidents/tasks/statuses change.
- Do not claim that reports or completed tasks represent tonnes of waste removed, litres of water saved, disease cases prevented, or emissions avoided unless those outcomes have been measured. Export incident data as a valid CSV file.
- Quote commas and embedded quotes correctly and neutralize formula-leading user-controlled fields before writing spreadsheet CSV.

## 10. README, setup, operation, and transparent limitations — complete

- Deliver complete, organized working source code and a README with setup/run commands; architecture; prioritization and duplicate-detection algorithms; environment variables, if any; deployment instructions; and an explanation of real data versus simulated data.
- README must include the problem statement, solution, sustainability impact, SDG mapping, key features, limitations, and future improvements.
- Map the project to SDG 6 Clean Water and Sanitation, SDG 11 Sustainable Cities and Communities (primary), SDG 12 Responsible Consumption and Production, and SDG 13 Climate Action. Link secondary goals to relevant recovery activities.
- Identify that browser-local data is local to the current browser/device rather than shared coordinator storage, and that all seed reports/locations are fictional demonstrations. Document that the score is a heuristic and no emergency/official advice, environmental testing, or professional inspection is replaced.
